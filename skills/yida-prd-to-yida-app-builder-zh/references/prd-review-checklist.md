# PRD / 蓝图审查清单

在建表、生成页面、写自动化之前，先用这份清单审查需求文档。目标是提前发现业务逻辑不顺，而不是把不成熟的需求机械落地。

## 1. 模块边界

检查：

- 这个模块解决哪个业务问题？
- 哪些流程属于本模块，哪些只是上下游协作？
- 是否把一个场景拆成太多表，或把多个不同场景塞进一张表？
- 是否存在“蓝图写了一个表，但实际应合并到已有入口”的情况？

输出：

- 模块范围
- 本轮做什么
- 本轮不做什么
- 需要用户确认的边界问题

## 2. 主数据和单据

先区分：

- 主数据：长期存在、被多处引用，例如门店、产品、供应商、设备、配件、人员、合同。
- 业务单据：一次业务动作，例如申请、登记、报修、检查、验收、入库、下架。
- 流程单据：需要审批、会签、多人处理或状态推进的记录。
- 报表/看板：从数据汇总展示，不应让用户重复录入。

常见问题：

- 把主数据当业务单据反复创建。
- 正式主数据应该由流程生成，却让用户手工新增。
- 下游表单重新输入上游已有字段。
- 同一实体有多个名称相近的表，来源和职责不清。

## 3. 流程闭环

每条链路都要回答：

- 起点是什么？
- 谁发起？
- 谁处理？
- 处理结果有哪些？
- 结果写回哪个表？
- 下游如何继续？
- 异常/驳回/不通过去哪？
- 结束条件是什么？

如果 PRD 只写了“通知某部门”但没写谁处理、处理后写回什么，要标为缺口。

## 4. 字段来源

逐字段判断：

- 手动填写
- 自动生成
- 关联选择
- 自动带出
- 公式计算
- 外部系统同步
- 自动化回写

风险点：

- “产品名称 / 门店名称 / 供应商名称 / 设备名称”等选择字段不应长期手填。
- 自动带出的字段通常应只读。
- 隐藏辅助字段如果参与自动化，应设置始终提交。
- 关键编号应稳定、唯一、可用于查询更新。

## 5. 权限和责任人

检查：

- 谁能新增？
- 谁能编辑？
- 谁只能查看？
- 谁审批？
- 谁被通知？
- 哪些主数据不允许普通用户手工改？

风险点：

- 系统生成的档案表默认所有人可编辑。
- 审批人、通知人、执行人没有字段承载。
- 同一个流程跨部门，但没有明确负责节点。

## 6. 自动化和通知

检查每个自动化候选：

- 触发表单
- 触发事件：新增、更新、审批通过、定时
- 触发条件
- 查询条件
- 新增/更新/通知/审批动作
- 去重策略
- 失败时如何发现

风险点：

- 纯新增导致重复数据。
- 用名称匹配导致误更新。
- 老记录缺隐藏辅助字段，更新时覆盖为空。
- 自动化命名不统一，后续难维护。

## 7. 集成与外部系统

检查：

- 是否涉及乐才、用友、每刻、海康、企迈、奥琦玮等外部系统？
- 哪个系统是主数据源？
- 同步方向是什么？
- 同步失败如何处理？
- 是否需要 SSO、API、连接器或机器人通知？

不要在外部系统字段来源未明确时，盲目建成本地手填字段。

## 8. 验证设计

在动手前设计测试：

- 最短成功路径
- 失败/不通过路径
- 重复提交路径
- 权限验证
- 自动化运行验证
- 数据回写验证

如果一个模块无法设计测试路径，说明需求还不够清楚。

## 9. 输出格式

审查后先输出：

```markdown
## 需求体检

### 可以直接落地
- 

### 需要修正后落地
- 

### 需要用户确认
- 

### 建议的表单/主数据拆分
- 

### 建议的闭环流程
- 
```

用户确认或授权后，再进入建表、字段、自动化和测试。

## 10. 问题分级

把需求问题按影响分级：

- **P0 阻断**：不确认就不能建。例如主数据来源不清、流程没有结束条件、关键处理人缺失、同一数据有两个冲突来源。
- **P1 高风险**：可以提出推荐方案，但建错会返工。例如字段来源不明、去重策略不清、通知对象不清、审批条件缺失。
- **P2 优化**：不影响主流程，但影响体验或维护。例如命名不统一、默认值缺失、列表视图不友好、UI 排版普通。

输出时把 P0 单独列出来，优先让用户确认；P1/P2 可以附推荐处理方式。
