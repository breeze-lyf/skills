# 宜搭应用分阶段交付清单

本文件是 `SKILL.md` 的详细阶段清单。执行复杂宜搭模块时，按阶段推进；阶段之间可以暂停、验收、换 Agent 接手。

## Phase 0：项目接入与现状盘点

目标：确认“现在有什么”，避免覆盖用户、同事或其他 Agent 的工作。

必做：

- 读取项目 `docs/` 下最新交接文档。
- 读取原始 PRD/蓝图/会议纪要。
- 确认应用 ID、模块范围、工作目录。
- 检查 `openyida login --check-only --json`。
- 拉取或回读相关表单 Schema。
- 拉取或审查自动化列表。
- 记录当前已有页面、表单、自动化、权限和已知缺口。

输出：

- 当前状态摘要。
- 本轮处理范围和不处理范围。
- 风险：线上多人修改、旧补丁、同事流程、登录状态、无法自动化配置的能力边界。

通过标准：

- 能说清当前线上状态来自哪里。
- 不依赖记忆或旧 `.cache` 判断当前配置。

## Phase 1：需求体检

目标：判断 PRD 能不能直接落地，提前指出业务逻辑问题。

检查：

- 模块边界是否清晰。
- 主数据和业务单据是否混淆。
- 是否存在“正式结果库”被当成手工录入表。
- 下游是否重复手填上游已有字段。
- 流程是否有起点、处理人、结果、写回对象、终点。
- 不通过、驳回、重复提交、撤销、下架等异常路径是否有去处。
- 通知、审批、定时任务是否只写了“提醒”，但没有责任人和完成判断。
- 外部系统同步方向是否明确。

输出：

- `需求体检 + 搭建方案`。
- P0/P1/P2 风险清单。
- 推荐表单拆分和主数据设计。
- 分批实施建议。

通过标准：

- P0 已让用户确认，或明确暂缓。
- P1/P2 已写入计划和交接文档。

## Checkpoint Diagnosis：诊断确认

必须停的情况：

- 主数据来源不清。
- 流程终点不清。
- 关键审批/责任人缺失。
- 可能把未经验证的数据写入正式库。
- 用户明确要求先审查，不让改线上。

可以继续的情况：

- 用户明确说“按你说的做”。
- P0 不存在，只有 P1/P2 优化项。
- 用户授权可以创建和提交测试表单。

## Phase 2：业务架构设计

目标：把“要建哪些表”升级为“业务对象如何流转”。

产物建议：

1. 主数据表：实体、唯一标识、来源、维护人、普通用户权限。
2. 业务单据表：触发场景、发起人、处理人、关键结果、写回对象。
3. 状态机：状态字段、状态值、变化来源、下游影响。
4. 关联矩阵：当前字段、关联对象、带出字段、只读、过滤规则。
5. 自动化矩阵：触发点、条件、动作、去重键、失败风险、验证方式。
6. 权限矩阵：角色、表单、数据范围、字段权限、操作权限。
7. 验证路径：成功路径、失败路径、重复提交、权限验证、状态回写。

通过标准：

- 每条主链路能回答“谁做什么，结果写回哪里”。
- 下游选择字段知道该关联谁。
- 自动化知道用什么稳定键查询或去重。

## Checkpoint Build Plan：实施计划确认

对齐：

- 本轮先做哪条主链路。
- 是否允许改线上 UI。
- 是否允许新增或禁用自动化。
- 是否允许提交测试数据。
- 是否需要保护同事创建的流程。
- 哪些模块暂不处理。

默认批次：

1. 主链路和主数据闭环。
2. 关联字段、自动带出和状态过滤。
3. UI 统一和移动端可用性。
4. 自动化、通知、审批、定时任务。
5. 报表、视图和管理看板。

## Phase 3：表单与主数据基础搭建

目标：建出正确的表单骨架和主数据基础。

检查：

- 表单名、导航分组、用途是否和模块边界一致。
- 主数据是否有稳定唯一编号。
- 系统生成字段是否只读。
- 业务结果库是否禁止普通用户随意新增/编辑。
- 隐藏辅助字段是否有明确用途。
- 文件、图片、成员、子表字段是否类型正确。

通过标准：

- 表单存在且 Schema 可回读。
- 关键字段 ID 可记录。
- 主数据来源和权限明确。

## Phase 4：UI 与录入体验优化

目标：让业务人员愿意用、少出错。

检查：

- 分区是否符合录入顺序。
- 电脑端是否适合两列。
- 手机端是否自动一列。
- 多行、附件、成员、子表是否独占整行。
- 自动带出字段是否只读。
- 隐藏字段是否不干扰用户。
- 必填项是否真有必要。

通过标准：

- 预览页面没有明显窄输入框、错位、遮挡。
- 业务人员能按自然顺序填写。

## Phase 5：关联、联动与数据一致性

目标：不让用户重复输入已有数据。

检查：

- 产品、门店、供应商、设备、合同、人员等选择字段是否关联。
- 关联目标是否是正确阶段的对象。
- 自动带出字段是否够用。
- 带出字段是否只读。
- 状态过滤是否限制下游可选范围。
- 隐藏辅助键是否始终提交。
- 自动化是否读取文本辅助字段而不是关联对象本体。

通过标准：

- Schema 回读能证明字段类型、回填、过滤正确。
- 关键下游表单不能选择错误状态的数据。

## Phase 6：自动化、审批、通知、定时任务

目标：让业务结果自动流转，而不是停在表单里。

检查：

- 自动化是否必要，还是只需要视图/报表。
- 触发事件是否正确：新增、更新、审批通过、定时。
- 触发条件是否防误触发。
- 查询/去重键是否稳定。
- 是新增、更新还是 UPSERT。
- 是否会重复生成正式主数据。
- 是否会用空字段覆盖已有主数据。
- 命名是否符合项目习惯。
- 创建人边界是否被尊重。

通过标准：

- 自动化列表可读。
- 异常检查无阻断错误。
- 关键自动化有测试实例证明结果。

## Phase 7：测试验收

目标：用证据证明业务链路通了。

至少测试：

- 最短成功路径。
- 不通过/驳回路径（如果已实现）。
- 重复提交/重复通过是否会重复生成。
- 上下架或状态变化是否影响下游可选范围。
- 普通成员权限和管理员权限。
- 自动化异常日志。

测试记录写入文档：

- 测试目标。
- 源表单实例。
- 目标表单实例。
- 关键字段结果。
- 是否通过。
- 是否需清理测试数据。

## Phase 8：交接沉淀

目标：让项目可持续，而不是只靠当前 Agent 记忆。

交接文档至少包含：

- 当前业务判断。
- 本轮完成项。
- 表单/字段/关联/权限/自动化清单。
- 创建/禁用/保留的流程。
- 同事流程边界。
- 测试记录。
- 已知风险。
- 下一步建议。

通过标准：

- 下一个 Agent 能从文档和线上状态继续。
- 用户能看懂当前项目做到哪、还差哪。
