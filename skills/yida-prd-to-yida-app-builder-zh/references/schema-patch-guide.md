# Schema Patch 使用指南

Schema Patch 是在宜搭设计器之外，直接修改表单 Schema 的方法。它适合把 PRD 中的字段、布局、关联、联动和过滤规则批量落到宜搭页面中，尤其适合多人协作和批量页面统一风格。

## 什么时候使用

优先使用 Schema Patch 的场景：

- 批量统一 UI：`PageSection` 分区、PC 两列、移动端一列、字段顺序。
- 调整控件属性：只读、隐藏、必填、提交行为。
- 配置基础关联：把文本字段替换或改造成 `AssociationFormField`。
- 配置数据联动：选择上游记录后自动带出编号、规格、厂家、门店、供应商等字段。
- 配置过滤规则：例如正式产品只允许选择 `已上架`，上架申请只允许选择 `未上架`。
- 批量修复同类页面的输入框宽度、成员组件错位、附件区被压缩等问题。

不优先使用 Schema Patch 的场景：

- 配置审批流、复杂通知、定时任务、复杂集成自动化。
- 需要确认真实用户交互，例如关联弹窗搜索、移动端实际表现、设计器高级配置。
- 线上页面刚被同事改过，但你还没有回读最新 Schema。
- Patch 文件过大，可能覆盖同事刚做的 UI 或字段。

## 标准流程

1. 回读线上 Schema：

```bash
openyida get-schema <APP_ID> <FORM_UUID> > .cache/schemas/<form>.json
```

2. 从最新 Schema 生成补丁，不要基于旧缓存直接改。

3. 优先生成小范围 patch：

```json
[
  {
    "action": "replace",
    "path": "/pages/0/componentsTree/0/children/1/children/0/children",
    "value": []
  }
]
```

4. 发布补丁：

```bash
openyida create-form patch <APP_ID> <FORM_UUID> .cache/patches/<patch>.json
```

5. 回读验证：

```bash
openyida get-schema <APP_ID> <FORM_UUID> > .cache/after_patch/<form>.json
node scripts/extract-yida-fields.js .cache/after_patch/<form>.json
```

6. 关键页面用浏览器预览 PC 和移动端。

7. 把变更写入项目交接文档。

## Patch 粒度原则

优先级从高到低：

1. 修改单个字段 props，例如 `behavior`、`submittable`、`dataFillingRules`、`dataFilterRules`。
2. 替换一个局部分区或一个布局容器。
3. 替换整个表单内容区域。
4. 替换整个 `componentsTree`。

越靠后的方式风险越高。整页替换前必须确认：

- 当前 Schema 是最新线上版本。
- 没有同事正在页面设计器里修改同一表单。
- 已备份 before/after Schema。
- Patch 中保留了所有原有字段、联动、隐藏辅助字段和权限相关配置。

## UI 布局规则

业务型 OA 表单默认遵守：

- PC 端可两列，移动端自动一列。
- `EmployeeField`、`AttachmentField`、`TextareaField`、`TableField`、图片、签字控件尽量独占整行。
- 自动带出的字段通常只读。
- 隐藏辅助字段应 `HIDDEN` 且可提交，供自动化使用。
- 关联字段应放在用户录入顺序靠前的位置，方便后续字段自动带出。
- 不要为了视觉对齐把字段压到过窄容器里。

## 关联和联动规则

关联字段应先判断业务阶段：

- 候选阶段关联候选对象，例如候选产品、需求单、登记单。
- 正式运营阶段关联正式主数据，例如正式产品库、门店档案、供应商档案。
- 汇总表优先由自动化生成或更新，不让用户重复手填。

自动带出字段要尽量只读，例如：

- 产品名称 -> 产品编号、规格、包装规格、口味、厂家。
- 门店名称 -> 门店编号、区域、负责人。
- 供应商名称 -> 供应商编号、联系人、电话、地址。

过滤规则要贴合状态：

- 上架申请：只选 `未上架`。
- 入库、抽检、下架：通常只选 `已上架`。
- 二次审厂：只选第一次审厂 `不合格` 的记录。

## 风险清单

常见风险：

- 用旧缓存生成 patch，覆盖同事最新 UI。
- 整页替换时漏掉隐藏辅助字段，导致自动化取不到编号。
- 把关联字段对象直接写入文本字段，导致产品名或门店名为空或变成对象。
- 只改 UI，不回读 Schema，实际字段类型没有变。
- 只用数据 API 测试，没验证真实关联弹窗选择。
- Patch 后没预览移动端，成员/附件/子表布局异常。

## 什么时候切浏览器

下面这些情况要切浏览器或真实宜搭后台：

- 关联字段在数据 API 中无法真实写入，只能通过 UI 弹窗选择验证。
- 需要检查设计器里组件宽度、拖拽布局、移动端实际效果。
- 需要配置 openyida/Schema 难以表达的高级后台能力。
- 需要确认同事创建的自动化节点细节，但 CLI 只能看到列表，不能看到完整画布。

切浏览器前要明确告诉用户为什么需要，并尽量打开新标签页，不占用用户当前页面。

## 交接记录模板

每次使用 Schema Patch 后，在项目文档记录：

```markdown
### Schema Patch 变更

- 表单：
- Patch 文件：
- 变更范围：
- 修改字段：
- 关联/联动/过滤：
- 回读验证：
- UI 预览：
- 风险和下一步：
```
