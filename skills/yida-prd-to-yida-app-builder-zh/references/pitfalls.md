# 踩坑与恢复方式

## PRD 不等于正确业务逻辑

问题：蓝图或 PRD 可能存在表单拆分不合理、主数据来源不清、流程只写通知不写处理结果、字段重复录入等问题。

处理方式：

- 建表前先做需求体检。
- 把“可以落地”和“需要确认”分开。
- 对明显不闭环的地方先提出修正建议。
- 不要为了满足文档字面描述而复制一个业务上多余的表。

## 旧 Schema 补丁覆盖新页面

问题：早期生成的补丁可能覆盖后来的 UI、字段或其他 Agent 的工作。

处理方式：

- 先拉当前线上 Schema。
- 优先做最小补丁，不要整表替换。
- 如果补丁文件很大，并且早于最近 UI 修改，先视为高风险。
- 应用后重新读 Schema，只比对这次想改的字段。

## UI 容器导致字段定位失真

问题：表单有嵌套 UI 容器时，某些更新命令可能只看到顶层 `PageSection`。按 label 新增字段时，字段可能被追加到视觉分区外。

处理方式：

- 用字段遍历脚本检查嵌套 Schema。
- 优先使用能深度查找字段的更新动作。
- 改布局后尽量打开预览。
- 不要把 `EmployeeField`、`AttachmentField`、`TextareaField`、`TableField`、签字或图片上传塞进窄列。

## 关联字段对象被写进文本字段

问题：把 `AssociationFormField` 的值直接写入文本字段，可能得到对象/JSON，而不是可读名称。

处理方式：

- 增加隐藏文本辅助字段，例如“对象名称文本”。
- 通过关联源的文本字段自动回填。
- 新增主数据时用辅助字段写入名称。
- 注意旧记录可能是在辅助字段存在前创建的，辅助字段可能为空。

## 空辅助字段覆盖成熟主数据

问题：UPSERT 自动化更新已有主数据时，把身份字段更新为隐藏辅助字段，但旧记录的辅助字段为空，导致成熟主数据被清空。

处理方式：

- 新增记录时写入名称、编号等身份字段。
- 更新已有记录时，不要用可选辅助字段覆盖成熟身份字段。
- 如果必须更新身份字段，先加非空条件。

## 结果库重复生成

问题：纯 INSERT 自动化会让同一业务对象多次进入正式结果库或主数据表。

处理方式：

- 先判断业务是否允许“一次事件一条独立结果”。
- 如果不允许，增加稳定来源编号。
- 按来源编号查询已有记录。
- 分支处理：存在则更新，不存在则新增。

## 用名称匹配记录

问题：名称可能重复，也可能后续修改。

处理方式：

- 使用稳定编号，例如流水号、来源编号、正式编号、门店编码、设备编码、合同编号。
- 隐藏辅助键字段，但设置始终提交。
- 提交下游表单后按编号验证目标记录。

## 修改同事自动化

问题：直接改同事创建的流程，可能破坏别人负责的链路。

处理方式：

- 修改前先列出自动化创建人。
- 把同事流程记录为依赖。
- 没有用户明确授权，不要修改同事流程。
- 替换自己创建的流程时，新建并验证后再禁用旧流程。

## openyida 能力边界

问题：CLI 能处理很多 Schema、数据、自动化操作，但不是所有宜搭设计器高级行为都能稳定表达。

处理方式：

- CLI 适合快速结构、Schema、数据和部分自动化。
- CLI 表达不了时，使用浏览器/UI。
- 不要猜测宜搭前端路由；优先从工作台真实入口进入。
- 用 `integration check`、运行日志和真实提交验证。
- 把任何手动或浏览器专属步骤写进文档。

## 权限漂移

问题：系统生成的主数据页面可能仍然对所有成员可编辑。

处理方式：

- 主数据表生成后审查默认权限。
- 普通成员只保留必要查看能力。
- 管理员和数据负责人保留管理权限。
- 权限调整后用普通成员视角验证。

## 交接文档漂移

问题：后续 Agent 分不清文档里哪些是当前状态、哪些是旧计划。

处理方式：

- 在文档顶部保留当前状态区。
- 历史流程明确标记为禁用或保留。
- 记录流程码和测试实例 ID。
- 未解决问题写成业务决策点，不要混成实现 bug。
