# 宜搭 PRD 到应用闭环搭建技能

把不一定完美的 PRD、蓝图方案、会议纪要或业务流程材料，分阶段转成可运行、可演示、可验证、可交接的宜搭应用模块。

核心原则：**不要把“建出表单”误认为“完成交付”**。先审业务，再判断项目是“客户演示 Demo”还是“生产落地实施”，再设计结构、页面、字段、样本数据、UI、关联、权限、自动化与验证方式。

本 Skill 可用于不同宜搭项目。模块、角色、字段和流程必须从用户材料、最新澄清和客户业务目标中动态推导。历史案例只是参考，不是默认模板；不得因为技能示例而引入材料中没有的财务、采购、BOM、生产、仓库、供应商、合同等模块。

## 工作流总览

```
Phase 0   项目接入与现状盘点
   读项目文档 / 原始 PRD / 当前线上 Schema / 当前自动化
   ▼
Phase 1   需求体检
   找业务断点、主数据不清、字段重复、流程不闭环、权限/通知/审批缺口
   ▼
[Checkpoint Diagnosis]  ← 关键节点：输出“需求体检 + 搭建方案”，P0 必须等用户确认
   ▼
Phase 2   业务架构设计
   模块边界 / 主数据 / 单据 / 状态 / 角色 / 自动化 / 验证路径
   ▼
[Checkpoint Build Plan] ← 关键节点：确认实施范围、优先级、测试授权、是否可提交测试数据
   ▼
Phase 3   表单与主数据基础搭建
   建表 / 补字段 / 导航分组 / 编号 / 隐藏辅助键 / 基础权限
   ▼
Phase 4   UI 与录入体验优化
   分区 / 电脑两列手机一列 / 只读隐藏 / 附件成员子表布局 / 预览验证
   ▼
Phase 5   关联、联动与数据一致性
   AssociationFormField / 自动带出 / 过滤规则 / 状态可选范围 / 防手填
   ▼
Phase 6   自动化、审批、通知、定时任务
   触发条件 / 查询键 / 新增或更新 / 回写状态 / 命名规范 / 创建人边界
   ▼
Phase 7   测试验收
   Schema 回读 / 自动化检查 / 真实测试提交 / 权限验证 / 异常路径
   ▼
Phase 8   交接沉淀
   更新 docs / 写清流程码、字段、测试记录、风险、下一步
```

**默认不要试图一步到位。** 宜搭项目经常有线上多人修改、PRD 不完整、浏览器后台配置限制、自动化状态不透明等情况。按阶段推进，每阶段都留证据。

详细阶段清单见 [references/phased-delivery.md](references/phased-delivery.md)。

## 工作模式

根据用户意图选择模式；不明确时默认 **混合型**。

| 模式 | 何时使用 | 行为 |
| --- | --- | --- |
| Demo/能力展示型 | 用户说“demo”“演示”“客户展示”“签约汇报”“能力闭环”“阿里生态展示”“不是落地项目” | 以 10-30 分钟演示路径为核心，优先设计页面、样本数据、AI/生态闭环、讲解顺序和高层可感知价值；不按生产系统验收口径堆权限、审批、真实接口和全量异常 |
| 需求体检型 | 用户只问“怎么做”“是否合理”“先审查” | 只输出诊断、方案和风险，不改线上 |
| 混合型（默认） | 用户要搭建/优化，但需求仍有不确定 | 先输出诊断和方案，P0 等确认；P1/P2 可列入后续执行 |
| 执行型 | 用户明确说“做”“继续处理”“可以测试提交” | 主动执行，但仍按阶段推进、验证、更新文档 |
| 接手型 | 用户要求换 Agent 接力、恢复进度 | 先读交接文档和线上状态，再继续，不从记忆重来 |

### Demo/能力展示型特殊规则

当项目被识别为 Demo/能力展示型时，所有阶段都按“演示闭环”重排：

- 目标不是一次性搭成客户生产可用系统，而是在演示环境中证明业务主线、阿里生态能力和宜搭搭建能力可以闭环。
- 先回答三个问题：演示给谁看、20 分钟内讲哪条业务故事、客户看完应相信什么价值。
- 产物优先级：演示主线 > 模块闭环 > 页面清单 > 字段与样本数据 > API/集成占位 > 后续落地扩展。
- 页面数量要克制，优先保留能串起闭环的 5-9 个页面；不要为了“像完整系统”而扩展范围外模块。
- 字段以支撑展示为准，保留关键筛选、状态、指标、关联、图片/附件、地图坐标、AI摘要和行动建议；不要做生产级全字段字典。
- 验证方式使用“演示路径预演、样本数据连贯性、页面跳转可讲通、图表能呈现、AI文案可解释”，不要强制要求真实测试提交。
- 客户可见文档、流程图和页面文案不得出现“假数据”“模拟数据”“不是落地项目”“用户要求”等内部表达；对外统一使用业务语言，如“终端经营数据”“巡店执行数据”“交易转化数据”“能力验证版本”“生态协同展示方案”。
- 只有用户明确要求生产落地时，才恢复完整权限、审批、真实接口、异常处理、审计和生产验收规则。

P0/P1/P2 分级：

- **P0：阻断实施**。主数据来源不清、流程起点/终点缺失、关键责任人缺失、会造成错误数据进入正式库、可能破坏同事流程。必须停下来确认。
- **P1：可带建议推进**。字段关联缺失、自动化去重风险、权限不严、通知审批缺口。写入方案，获得授权后修。
- **P2：体验和维护优化**。UI 密度、命名一致性、文档细化、报表视图。可在阶段内顺手做，但不得影响主链路。

## 开始时必须做

### 1. 读项目材料

优先顺序：

1. 用户在对话中后续澄清的业务规则和纠偏，优先级最高。
2. 原始 PRD、蓝图、`.docx`、`.html`、会议纪要、流程图、截图。
3. 当前项目 `docs/` 下的交接和审查文档。
4. 线上最新 Schema 和自动化状态；Demo 项目若尚未创建应用，可先输出搭建 PRD。
5. 本地 `forms/`、`.cache/`、patch 脚本，仅作为参考，不能替代线上状态。

历史案例文件只在用户明确提到对应项目或需要参考实现套路时读取，不能作为新项目的默认业务范围。

### 2. 检查线上状态

如果项目使用 `openyida`，在项目 `forms/` 目录优先运行：

```bash
openyida login --check-only --json
openyida integration list <APP_ID> --json
openyida integration check <APP_ID> --json
```

修改字段或 UI 前，先拉当前线上 Schema。不要直接相信旧 `.cache`，因为用户、同事或其他 Agent 可能已经改过线上应用。

### 3. 建立或更新交接文档

每轮关键变更后都要更新项目文档。没有现成文档时，用 [references/handoff-template.md](references/handoff-template.md) 创建。

文档至少写：

- 本轮处理范围和未处理范围；
- 当前业务判断；
- 表单/字段/关联/权限/自动化变更；
- 测试实例和验证结果；
- 风险、遗留问题和下一步。

## Checkpoint Diagnosis：需求体检硬节点

建表或改线上之前，先输出一版“需求体检 + 搭建方案”。除非用户已经明确授权继续执行，否则这里必须停一下。

输出应包括：

1. **模块边界**：本轮做什么，不做什么，上下游是什么。
2. **业务对象**：主数据、业务单据、流程单据、报表/看板、外部系统。
3. **主链路**：起点、关键节点、结束条件、异常/驳回/不通过路径。
4. **字段来源**：手填、自动生成、关联选择、自动带出、公式、外部同步、自动化回写。
5. **风险分级**：P0/P1/P2，尤其指出 PRD 自身不通顺的地方。
6. **建议方案**：表单拆分、字段关联、权限策略、自动化策略、验证路径。
7. **实施批次**：先做主链路，再做体验，再做报表/通知/定时等增强项。

用 [references/prd-review-checklist.md](references/prd-review-checklist.md) 和 [references/business-object-canvas.md](references/business-object-canvas.md) 做审查。

## 阶段执行准则

### Phase 2：业务架构设计

先回答这些问题，再动手：

- 哪些是主数据？谁维护？普通用户能不能编辑？
- 哪些是业务单据？提交后结果写回哪里？
- 哪些字段必须关联上游记录，不能手填？
- 哪些状态驱动下游可选范围？
- 哪些节点需要审批、通知、定时提醒？
- 哪些自动化需要新增、更新、UPSERT 或状态回写？
- 最短成功路径和异常路径分别怎么验证？

常见模块模式见 [references/domain-patterns.md](references/domain-patterns.md)。

### Phase 3：表单与主数据基础搭建

使用 `openyida` 做基础结构最合适：建表、补字段、更新基础 Schema、移动导航分组。

但要记住：`openyida` 通常不能完整解决所有高级配置。遇到关联表单类型转换、复杂联动、审批流、通知、定时任务、复杂 UI 调整时，准备切换到浏览器自动化或宜搭后台。

创建主数据时要判断来源：

- 长期基础档案：可由管理员维护。
- 业务结果库：应由流程通过后生成，不应普通用户手工新建。
- 候选库和正式库要分清，不能让下游选错阶段的数据。

### Phase 4：UI 与录入体验优化

业务系统 UI 应该克制、清晰、易扫读，不追求花哨。

优先使用 **Schema Patch** 做可结构化表达的 UI 和字段配置变更：分区、布局、字段顺序、只读/隐藏、基础关联、联动、过滤规则等。不要一上来就打开浏览器手工拖拽，除非配置无法用 Schema 表达，或必须通过真实 UI 验证交互。

优先规则：

- 电脑端可两列，手机端自动一列。
- `EmployeeField`、`AttachmentField`、`TextareaField`、`TableField`、签字、图片等控件尽量独占整行。
- 分区标题、字段顺序、只读/隐藏状态要服务实际录入顺序。
- 自动带出字段通常只读，避免用户改出不一致数据。
- 预览电脑端和移动端，避免输入框过窄、成员组件错位、附件区被压缩。

Schema Patch 方法见 [references/schema-patch-guide.md](references/schema-patch-guide.md)。

### Phase 5：关联、联动与数据一致性

凡是已有上游记录的数据，优先关联选择，不要手填。

判断关联目标：

- 候选阶段：关联候选主数据或上游申请单。
- 正式运营阶段：关联正式主数据。
- 汇总表：优先由上游单据自动生成/更新，不让用户重复填。

必须检查：

- `AssociationFormField` 是否关联正确表单；
- 自动带出字段是否完整；
- 带出字段是否只读；
- 过滤规则是否限制可选状态；
- 隐藏辅助字段是否始终提交；
- 自动化使用稳定编号，而不是名称。

可用脚本：

```bash
node scripts/extract-yida-fields.js <schema.json>
node scripts/audit-entity-fields.js <schema-dir> '产品|门店|供应商|设备|合同'
```

字段关联、联动和过滤规则如果能在 Schema 中稳定表达，优先用 `openyida create-form patch` 发布；如果关联字段真实提交、设计器高级配置或页面预览无法通过 Schema/CLI 验证，再切换到浏览器自动化。

### Phase 6：自动化、审批、通知、定时任务

自动化不是“能建就建”，要先判断触发是否真的对应业务结果。

每条自动化都要明确：

- 触发表单和事件；
- 触发条件；
- 查询/去重键；
- 新增、更新、UPSERT、通知、审批、定时任务中的哪一种；
- 成功后写回哪个对象和哪个状态；
- 失败或重复提交怎么处理；
- 命名是否符合项目习惯；
- 是否属于同事创建的流程，能不能改。

新建或重建自动化时，遵守本地命名习惯，例如 `【表单名】动作`。同事创建的流程默认只审查引用，不直接修改，除非用户明确授权。

自动化审查可用：

```bash
node scripts/audit-integrations.js <integration-list.json>
openyida integration check <APP_ID> --json
```

### Phase 7：测试验收

不要只凭“配置看起来对”宣布完成。至少做四类验证：

1. **Schema 回读**：字段类型、fieldId、隐藏/只读、联动、过滤、提交行为。
2. **自动化检查**：启用/禁用状态、命名、创建人、异常日志。
3. **演示/测试提交**：Demo 项目用展示样本跑通讲解路径；生产落地项目在用户允许时用测试数据跑最短成功路径。
4. **权限/体验验证**：普通成员和管理员权限差异；电脑和移动端可用性。

测试数据要写入交接文档，并标注是否需要后续清理。

### Phase 8：交接沉淀

完成一批就更新文档，不要等最后。

交接文档要让下一个 Agent 只靠文档和线上状态就能继续：

- 当前业务判断；
- 已改哪些表单字段；
- 哪些字段关联了哪个目标；
- 哪些自动化已启用、禁用、保留；
- 哪些流程是同事创建，不能乱动；
- 测试实例、测试结果；
- 已知风险和下一步建议。

```

已处理：
- ...

验证结果：
- Schema：...
- 自动化：...
- 测试数据：...

发现的问题：
- P0：...
- P1：...
- P2：...

下一阶段建议：
1. ...
2. ...

需要你确认：
- ...
```

如果用户已授权持续执行，P1/P2 不必每次都停，但必须写进文档。P0 必须停。

## 工具选择策略

| 任务 | 首选方式 | 说明 |
| --- | --- | --- |
| 建表、补基础字段、读 Schema | `openyida` | 快，但高级能力有限 |
| 深度字段审查 | 本 Skill `scripts/` | 减少人工漏看 |
| UI 高级排版、后台配置 | 浏览器自动化/宜搭后台 | 不猜 API，优先走真实 UI |
| 自动化列表和异常 | `openyida integration` + 审查脚本 | 先看现状，别重复建 |
| 审批流/通知/定时 | 宜搭后台或对应宜搭技能 | 建前先设计触发和责任人 |
| 文档沉淀 | 项目 `docs/` | 每批次更新 |

需要完整插件和子 Skill 选择规则时，读 [references/tool-map.md](references/tool-map.md)。

## 实施防护栏

- 不要用旧补丁覆盖整张表 Schema，除非确认它基于当前线上 Schema。
- 不要把 PRD 字面描述机械建成表；PRD 可能有业务逻辑错误。
- 不要让已有主数据字段继续手填，特别是本项目范围内的核心对象，例如门店、产品、人员、巡店任务、地图点位、经营指标等；供应商、设备、合同等仅在材料明确出现时才纳入。
- 不要用名称匹配记录，优先用稳定编号。
- 不要让隐藏辅助字段空值覆盖成熟主数据。
- 不要直接修改同事创建的自动化，除非用户明确授权。
- 不要只做 UI 而忽略字段来源和流程写回。
- 不要只建自动化不测试；至少查异常日志，关键链路尽量提交测试数据。
- 不要在完成后只说“已完成”，必须写明怎么验证。

踩坑和恢复方式见 [references/pitfalls.md](references/pitfalls.md)。

## 完成标准

说“完成”之前，至少确认：

- 需求体检里的 P0 已解决或用户明确决策。
- 主链路能说清：起点、处理人、状态变化、写回对象、终点。
- 关键选择字段已关联正确对象，并有必要的自动带出和过滤规则。
- 主数据权限合理，普通用户不能随意破坏结果库。
- 自动化命名、触发、条件、查询键、状态回写可解释。
- `openyida integration check` 或等效检查没有阻断异常。
- 用户允许时，Demo 项目至少一条演示样本跑通关键链路；生产项目至少一条测试数据跑通关键链路。
- 项目文档已更新，下一位 Agent 可接手。
