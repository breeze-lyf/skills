# 启动会到 PRD 工作流

## 用途

把“宜搭项目启动会/需求沟通/客户现有单据/业务表单/合同范围/实施清单”整理成稳定的客户确认版 PRD。产物既要让客户能对照现有表单，也要体现未来宜搭应用页面、字段来源、带出/联动、业务闭环和待确认问题。若本次是客户展示 Demo，则 PRD 应优先服务演示主线、能力闭环和商业价值表达，而不是生产系统实施验收。

本技能适用于不同业务范围的宜搭项目，例如市场巡检、门店地图、AI 知识库、经营看板、流程审批、客户服务、供应链协同等。不得把任何行业链路写死为默认内容；只有材料明确出现或客户明确要求时，才可以写入对应模块。

### Demo/能力展示项目模式

当用户说明项目用于 `demo`、`客户展示`、`签约汇报`、`能力展示`、`阿里生态闭环`，或明确说“不是落地项目”时，进入 Demo/能力展示项目模式：

- PRD 不是生产落地 SRS，而是宜搭 Demo 搭建说明 + 客户可讲解的能力闭环方案。
- 第一优先级是确定演示对象、演示时长、业务故事、模块闭环和讲解顺序。
- 第二优先级是把每个模块拆成宜搭可搭页面、关键字段、样本数据口径、图表/地图/AI交互和页面跳转。
- 不要扩展财务、采购、BOM、生产、仓库、委外、合同等范围外模块，除非用户或材料明确要求。
- 不要求真实接口全部打通；API 可分为“演示样本可替代”“需商用 Key/授权”“后续落地接入”。客户可见文档中不使用“假数据/模拟数据”作为卖点或主说明。
- 页面数量保持克制，优先 5-9 个能讲完闭环的页面；字段只保留支撑演示、筛选、看板、地图、AI摘要和行动闭环的关键字段。
- 客户可见表达必须体面，不写用户 prompt、内部过程、纠错痕迹、`不是客户生产可用系统`、`所有数据都是假数据` 等内容。

## 必要输入

开始写 PRD 前，先向用户索要或在本地定位这些材料：

- 会议材料：启动会纪要、会议录音转写、闪记、需求沟通记录、已有总结。
- 范围材料：项目实施清单、已签合同、报价单、SOW、方案书、模块清单、交付范围、验收标准。
- 客户表单：客户当前使用的 Excel、Word、PDF、图片表单，必须包含所有 sheet。
- 参考文档：客户或同类项目的 PRD/需求规格说明书模板。
- 项目信息：客户名称、项目名称、当前文件夹、输出目录。
- 业务信息：从材料中动态识别业务角色、组织、对象、流程、地图/报表/AI/集成/移动端等能力边界，不预设销售、BOM、采购、仓库、生产、财务等固定角色。
- 规则信息：命名规则、编码规则、编号规则、审批规则、权限规则、集成边界。

如果某类表单缺失，不要让页面空着。应按已确认的项目目标和业务逻辑先设计宜搭页面，标注“客户原始表单状态：暂未提供，先按系统逻辑设计”，并列出待确认问题。缺失资料不能成为套用通用 ERP/制造/财务模板的理由。

## 标准产出

完整 PRD 任务默认应输出：

- 客户确认版 PRD/DOCX：封面、目录、系统概述、业务流程、功能需求、字段布局、业务规则、待确认事项。
- 客户原始表单截图文件夹：每个 Excel sheet 或原始表单页一张图片。
- 已插入截图的 PRD：每个页面末尾保留“客户原始表单截图：”并插入对应图片。
- 客户表单映射表：原始文件/sheet -> 客户当前表单 -> 系统对应页面 -> 处理方式。
- 业务逻辑闭环表：业务域、角色、页面、上游、下游、输入输出字段、规则、待确认。
- 字段闭环表：页面、字段、类型、必填、来源/默认/联动、计算规则、下游使用、是否可编辑。
- 项目流程图/泳道图：按项目真实角色展示核心业务对象、页面、数据和任务流转。默认优先保证客户可读性和视觉专业度；只有用户明确需要可编辑源文件时，才使用 next-ai-draw-io / draw.io 生成 `.drawio`。
- 缺失资料清单：向客户继续索要的单据、规则或确认项。

Demo/能力展示项目的标准产出可调整为：

- Demo 版 PRD/DOCX：项目定位、演示主线、模块闭环、宜搭页面、字段、样本数据准备、AI/生态能力、讲解路径、后续落地扩展。
- 宜搭页面与字段矩阵：每个页面的字段、控件类型、样本数据来源、展示目的、关联节点。
- 演示流程图/泳道图：按平台或角色展示主流程、数据支撑和经营闭环反馈。
- 演示脚本：建议 10-30 分钟讲解顺序、每页讲什么、客户应看到的价值点。

如果用户只要求其中一个阶段或一个产物，只交付该阶段，并说明后续阶段还没做。

## 阶段制工作流

必须按阶段推进。每个阶段都有输入、动作、输出和门禁。除非用户明确只做某一阶段，否则不要跳过前置阶段直接写 PRD。

### Phase 0：输入与范围契约

- 目标：明确项目边界、已有材料和本次要交付什么。
- 输入：会议材料、实施清单、合同、报价/SOW/方案、模块清单、交付范围、验收标准、客户材料文件夹、参考 PRD、输出目录、编码/命名/审批/集成规则。
- 动作：
  - 确认源文件路径和输出目录。
  - 区分“范围材料”和“需求发现材料”。
  - 从合同/实施清单中提取范围内模块、范围外模块、交付物、验收口径、实施阶段和商业约束。
  - 判断本次任务是完整 PRD、表单映射、ER/字段闭环、截图插入，还是旧文档修订。
  - 判断本次任务是生产落地项目还是 Demo/能力展示项目；Demo 项目必须先定义演示主线和能力闭环，不按生产实施范围扩展。
  - 明确“范围内 / 范围外 / 仅为背景”的边界。对未在材料中出现的模块，默认不得写入功能需求。
  - 识别宜搭应用类型：流程审批、数据采集、台账报表、经营看板、地图可视化、任务派发、移动端巡检、AI 知识库、外部集成、门户/权限等。
  - 记录假设和缺口。
- 输出：
  - 输入材料清单
  - 项目范围基线
  - 项目类型与业务对象清单
  - 负面范围清单
  - 本次输出契约
  - 假设与风险清单
- 进入下一阶段门禁：
  - 源目录和输出目录明确。
  - 交付物明确。
  - 实施/合同范围已提供，或明确标记缺失。
  - 合同范围与会议需求不一致时，已列为风险。
  - 关键缺失输入已获得或已写入假设。

### Phase 1：客户材料盘点与规范归档

- 目标：让客户材料可追溯、可复用、可截图。
- 输入：客户原始文件夹、已有归档目录。
- 动作：
  - 递归列出所有文件。
  - 对 Excel 列出每个 workbook 和所有 sheet。
  - 复制文件到规范目录，不移动、不覆盖原件。
  - 按业务域、阅读顺序、表单含义重命名。
  - 生成命名分类清单。
- 输出：
  - 规范客户材料目录
  - 命名分类清单
  - workbook/sheet 盘点表
- 进入下一阶段门禁：
  - 每个源文件都出现在清单中。
  - 每个规范文件都存在。
  - Excel 已盘点 sheet，而不是只看文件名。

### Phase 2：会议与业务主线提炼

- 目标：从启动会和沟通记录里提炼业务链路。
- 输入：会议转写、会议纪要、聊天记录、已有总结。
- 动作：
  - 提取业务域、角色、主流程、决策、约束、待确认。
  - 识别核心业务对象和编号。对象必须来自材料，例如门店、渠道、产品线、巡检任务、地图点位、预警事件、知识库条目、AI 分析任务、经营指标等；不要预设生产订单、BOM、采购订单、入库、库存、出货、开票、回款、凭证。
  - 提取价值逻辑：客户为什么做、业务痛点是什么、可量化指标是什么、AI/自动化/宜搭能产生什么增量价值。
  - Demo 项目要额外提炼“客户高层能听懂的一句话价值”“20 分钟演示路径”“三段式闭环：洞察 -> 执行 -> 复盘/增长”。
  - 区分已确认事实和推断假设。
- 输出：
  - 业务主线摘要
  - 角色/部门清单
  - 核心业务对象/编号清单
  - 范围外禁写模块清单
  - 价值目标和指标清单
  - 待确认问题清单
- 进入下一阶段门禁：
  - 至少识别一条端到端业务路径。
  - 不确定的核心关联已标注待确认。

### Phase 3：客户表单到系统页面映射

- 目标：决定要建哪些系统页面，以及每张客户表单对应哪里。
- 输入：规范材料清单、sheet 清单、Phase 2 业务主线。
- 动作：
  - 将每张表单或需求点分类为宜搭基础数据表、流程表单、任务表、明细表、台账报表、地图页面、看板页面、AI 页面、集成来源、打印模板。
  - 一份 workbook 多个用途时拆成多个系统页面。
  - 标记重复表单、报表型表单、打印模板、缺失表单。
  - 将审批/签字栏从录入字段中拆出，放到“审批/流转”。
- 输出：
  - 表单-页面映射表
  - 缺失资料清单
  - 按业务域分组的页面清单
- 进入下一阶段门禁：
  - 每个 workbook/sheet 都已映射、拆分或明确排除。
  - 每个 PRD 页面都有来源状态：客户已提供 / 系统推导 / 客户暂未提供。

### Phase 4：PRD 骨架与文档架构

- 目标：先建立稳定的客户确认版文档框架。
- 输入：页面清单、业务域、参考 PRD 风格。
- 动作：
  - 生成封面、目录、引言、系统概述、用户角色、业务框架、功能需求、数据与集成、AI能力与安全边界（适用时）、待确认事项。
  - Demo 项目封面和摘要要像客户展示方案，不要像内部实施文档；正文可写“能力验证版本/客户展示方案”，但不要在核心页反复强调演示数据或未落地。
  - 功能需求按业务域/角色分组，不要写成平铺列表。
  - 有编码/命名/编号规则时放入系统概述或规则章节。
- 输出：
  - PRD 骨架 DOCX 或 Markdown
  - 章节编号和页面编号方案
- 进入下一阶段门禁：
  - 有封面和目录。
  - 第 3 章按业务域分组。
  - 页面标题稳定，可用于后续插入截图。

### Phase 5：页面布局与字段设计

- 目标：把每个页面设计成客户能看懂、未来系统也能落地的表单。
- 输入：表单映射、客户原始表单、PRD 骨架。
- 动作：
  - 优先做客户可读的系统表单布局，而不是纯技术字段表。
  - 表单样式必须尽量模拟未来用户使用时的系统页面/系统报表，而不是只列“字段名称、字段类型、来源”的清单。
  - 主表字段用系统化表单原型呈现：分区标题行（如“基础信息”“销售订单基础信息”）、字段名/取值规则成对排列，常见为 4 列或 6 列网格；字段名列可使用浅灰底和加粗，取值规则列写“手动填写”“规则生成”“客户档案带出”“自动计算”等。
  - 短字段用成组表单网格，长文本用整行或跨列字段，重复数据用独立明细表/子表；明细表应包含表头和一行取值规则示例，让客户能想象实际填报界面。
  - 不要把系统页面的“表单样式”写成内部字段矩阵；字段矩阵只用于字段闭环表或附录。
  - 可结构化的大段文本必须拆成字段或明细表。
  - 必填字段加 `*`。
  - 由其他页面带出、默认、选择关联的字段名加粗。
  - 来源/取值列必须写明项目真实来源，例如 `门店档案带出`、`地图点位带出`、`巡检任务关联`、`知识库检索`、`默认当前人员`、`自动计算`。只有材料明确存在生产、采购等模块时，才可使用 `生产订单带出`、`采购订单明细带出` 等表达。
  - 审批/签字不要放进主表单，单独写 `审批/流转：...`。
- 输出：
  - 已设计字段布局的功能页面
  - 页面级业务规则
  - 页面级待确认事项
- 进入下一阶段门禁：
  - 每个页面有表单类型、字段标记、接近系统界面的表单原型/明细表、业务规则、截图标签。
  - 表单原型不能只是字段清单；客户应能通过 PRD 大致看出未来系统表单的分区、字段排布、明细区域和填报方式。
  - 只要能从业务逻辑推导，页面不能只写“待补充”。

### Phase 6：业务逻辑闭环与字段闭环

- 目标：确保 PRD 不是一堆孤立表单，而是端到端业务系统。
- 输入：Phase 5 功能页面。
- 动作：
  - 追踪核心业务对象/编号在页面之间的流转。
  - 为字段补充来源、默认值、联动、计算规则、下游使用。
  - 检查每个范围内页面是否都有上游依据和下游使用。不得检查或补造范围外模块。
  - 未确认的业务选择保留为待确认，不要写死。
  - 生成或更新业务逻辑闭环表。
  - 生成或更新字段闭环表。
  - 生成或更新项目流程图/泳道图。
- 输出：
  - 已闭环的 PRD 字段逻辑
  - 业务逻辑闭环表
  - 字段闭环表
  - 项目流程图/泳道图
  - 可选 ER 表
  - 未闭环问题清单
- 进入下一阶段门禁：
  - 主链路可追溯，且必须来自项目材料。例如市场巡检类项目可能是：策略目标 -> 门店/渠道样本 -> 地图可视化 -> 巡店任务派发 -> 移动端反馈 -> AI识别/评分 -> 预警与复盘 -> 经营看板。
  - 不确定链路已标注待确认。
  - 每个关键页面都有上游来源、下游去向和责任角色。
  - 每个关键字段都有来源/默认/联动和下游使用，或标为独立手填。
  - 流程图包含主要角色、核心业务对象和真实流转节点。

### Phase 7：截图导出与 PRD 插入

- 目标：让客户能在 PRD 中直接对照原始表单。
- 输入：规范客户文件、最终页面标题。
- 动作：
  - 将每个 Excel sheet 或原始表单页导出为图片。
  - 图片命名为 `规范文件名__sheet名.png`。
  - 在对应功能页面末尾插入截图，位置在业务规则和待确认事项之后。
  - 固定标签使用 `客户原始表单截图：`。
- 输出：
  - 原始表单截图文件夹
  - 已插入截图的 PRD
- 进入下一阶段门禁：
  - 插入图片数量与截图映射一致。
  - 每张图有 `原表：...` 标题或清晰文件名。

### Phase 8：Harness、视觉检查与交付

- 目标：降低输出差异，交付前发现结构缺失。
- 输入：最终 PRD DOCX 和相关产物。
- 动作：
  - 运行 `scripts/check_prd.py`。
  - 如果可用，渲染 DOCX 做视觉检查；不可用时用 QuickLook/结构检查降级。
  - 修复缺失标题、截图标签、字段标记、逻辑关键词、审批字段混入表格等问题。
  - 最终回复提供交付文件和简短校验结果。
- 输出：
  - 最终 PRD
  - 映射表/闭环表/流程图/缺失清单等附属文件
  - 校验结果摘要
- 交付门禁：
  - harness 通过，或明确说明例外。
  - 最终回复只链接真正有用的交付物。

## 强制闭环产物

完整 PRD 任务默认必须产出以下三类闭环内容，除非用户明确排除。可以嵌入 PRD，也可以单独生成文件。闭环内容必须围绕项目真实范围生成，不能使用固定示例替代。

### 业务逻辑闭环

- 目的：证明每个系统页面都属于端到端业务链路。
- 格式：表格或电子表格。
- 必填列：
  - 业务域
  - 角色/负责人
  - 系统页面
  - 页面类型
  - 上游来源
  - 关键输入字段
  - 下游去向
  - 关键输出字段
  - 业务规则
  - 待确认事项
- 最小闭环路径：
  - 根据项目材料生成，不设固定路径。
  - 若是市场/门店/巡检/AI 项目，应优先检查 `业务目标 -> 样本/对象 -> 数据采集/集成 -> 地图/看板呈现 -> 任务派发 -> 移动端反馈 -> AI识别/分析 -> 预警/复盘 -> 经营决策` 是否闭环。
  - 若是流程审批项目，应检查 `申请 -> 审批 -> 执行 -> 归档 -> 报表/通知` 是否闭环。
  - 若是供应链或生产项目，只有材料明确出现时才检查订单、BOM、采购、库存、生产、财务链路。

### 字段闭环

- 目的：避免字段孤立、来源不清、下游不用。
- 格式：字段矩阵表或电子表格。
- 必填列：
  - 页面
  - 字段名称
  - 字段类型
  - 是否必填
  - 来源/默认/联动
  - 计算规则
  - 下游使用
  - 是否可编辑
  - 待确认事项
- 规则：
  - 必填字段使用 `*`。
  - 带出/默认/选择关联字段在 PRD 布局中加粗。
  - 带出字段必须写明来源页面，例如 `门店档案带出`、`巡店任务带出`、`地图点位带出`、`客户档案带出`。示例不得替代项目真实来源。
  - 计算字段必须写 `自动计算`，并用业务语言说明计算口径。

### 表单 UI 样式

- 目的：PRD 中的字段布局要像未来系统页面，客户可以直观看到页面长什么样，而不是技术字段字典。
- 统一样式：
  - 表格必须使用黑色实线边框，禁止虚线、浅灰虚线或不完整边框。
  - 分区标题使用浅灰底、上下居中、水平居中、加粗，例如 `门店基础信息`、`巡检任务信息`、`知识库条目信息`。标题必须来自项目范围。
  - 字段名称单元格使用浅灰底、加粗；字段值/取值说明单元格使用白底。
  - 表格宽度尽量铺满页面可用宽度，整体风格与客户已认可的表单或本项目宜搭页面形态一致。
- Word/DOCX 排版细节：
  - 已经形成客户认可风格的表单网格，不要为了“优化”而自动重排字段结构；优先保留原有 4 列或 6 列字段网格、分区顺序和明细表形态。
  - 表格普通字段文字应小于正文和章节标题，避免 10.5pt 以上的大字撑高行距；通常使用 9pt 左右，分区标题可略大但不要压过章节标题。
  - 单元格内边距要克制，避免上下留白过大；默认应使用紧凑内边距，并清除单元格段落的前后间距。
  - 表格行高应以内容可读为准，使用较低的最小行高或自然行高；禁止使用过高固定行高导致表格像大卡片一样松散。
  - 明细表标题行、字段表分区标题行、规则表标题行都必须水平居中且垂直居中。
  - 大标题、章节标题、表单章节元信息保持文档原有层级，不随表格字段字号一起缩小。
- 字段长度规则：
  - 短字段可以一行三组：`字段名 / 取值说明` × 3。
  - 中长字段一行最多两组，避免挤压换行。
  - 长文本、多选项、规则说明、附件说明、技术要求、打印说明必须独占整行或使用两列表格。
  - 明细字段超过 8 列时，优先拆成多个子表或把次要字段放到后续明细表，避免横向拥挤。
  - 客户原始打印模板的固定多行空白表格不要原样铺进系统字段设计；系统页面用可增删行子表表达，客户原始长表放到 `客户原始表单截图：` 后对照。
- 检查：
  - 页面上不能出现字段文字被明显挤压、长字段塞进小格子的情况。
  - 不要为了凑成一行三组而牺牲可读性。
  - 生成后至少抽查长字段页面，如巡检记录、AI分析结果、策略洞察、知识库条目、异常预警或本项目实际长文本页面。
  - Demo 项目字段矩阵要轻量：优先保留能驱动地图、看板、AI问答、巡店闭环和交易回流的字段；不要为了生产完整性补齐大量审核、财务、法务、审计字段。

### 项目流程图/泳道图

- 目的：一图说明角色交接、页面关系、数据流和任务闭环。
- 格式：优先输出客户可读的泳道图或模块闭环图。若用户明确要求可编辑源文件，再使用 [DayuanJiang/next-ai-draw-io](https://github.com/DayuanJiang/next-ai-draw-io) / draw.io 生成 `.drawio` 并导出 PNG/SVG；若用户更重视美观或明确否定 draw.io，应使用本地绘图脚本、PPT/图片生成或其他更适合排版的方法。
- 必须包含的泳道/分区：从项目材料中动态抽取，例如品牌/市场、渠道/门店、巡店人员、区域管理、AI分析、经营管理、宜搭平台/集成等；不得默认包含销售、BOM、采购、仓库、生产、财务。
- 节点规则：
  - 只放入范围内页面、业务对象和集成节点。
  - 对“背景信息”只可作为目标或约束，不可扩展成系统功能。
  - 节点名称必须与 PRD 页面清单和业务逻辑闭环表一致。
- 连线规则：
  - 泳道图必须使用水平/垂直正交连线，避免斜线、随意穿越节点、箭头贴边不齐。
  - 主业务流、任务流转、闭环回流均使用实线箭头；图中讲解时要顺着走的路径不能虚线化。
  - 虚线只用于基础数据支撑、规则引用、接口校验、权限/授权验证等“不代表流程先后”的辅助关系，且必须在图例或备注中说明。
  - 连线尽量从节点中心锚点出入，箭头方向与流程阅读方向一致；长回流线贴网格或泳道边界走线。
  - 交叉线超过 2 处时，应调整节点顺序或拆为“主流程图 + 数据闭环图”，不要用复杂斜线硬连。
- 规则：不要做装饰图。流程图必须与 PRD 页面清单和业务逻辑闭环表一致，不能出现 PRD 中没有依据的模块。

## 实现方法

不同交付物使用不同方法。工作记录或最终总结中要说明采用了哪种方法，便于复现。

### 客户材料整理

- 方法：复制原始文件到规范目录，不移动、不覆盖源文件。
- 工具：`find`、Python `shutil.copy2`、`openpyxl` 读取 `.xlsx` sheet、`xlrd` 读取 `.xls` sheet。
- 输出：规范目录、规范文件名、命名清单。
- 检查：每个源文件在清单中出现一次；每个规范文件存在。

### Excel/sheet 截图导出

- 方法 A：如果 LibreOffice 可用，优先通过 LibreOffice/PDF/图片链路渲染，保真度更高。
- 方法 B：稳定降级方案，使用 Python workbook 解析 + PIL 绘图，保留值、合并单元格、基础底色、边框、行列尺寸和换行。
- 工具：`openpyxl`、`xlrd`、`PIL`。
- 输出：每个 sheet 一张 PNG，命名为 `规范文件名__sheet名.png`。
- 检查：截图数量应与计划插入 sheet 数一致；PRD 中引用的图片都存在。

### DOCX PRD 生成

- 方法：用脚本或结构化模板确定性生成 DOCX，不依赖手工一次性编辑。
- 工具：`python-docx`。
- 输出：基础 DOCX 和可选 Markdown 摘要。
- 布局规则：
  - 短字段用成组字段表。
  - 重复明细用分区明细表。
  - 长文本用整行。
  - `审批/流转` 单独成段。
  - 截图放在页面规则之后。

### PRD 截图插入

- 方法：按功能页标题定位，在 `客户原始表单截图：` 后插入图片标题和图片。
- 工具：`python-docx`。
- 输出：已插入截图的最终 DOCX。
- 检查：图片数量增加，截图标题以 `原表：` 开头。

### 字段逻辑 / ER 表

- 方法：从页面对象和业务链路生成，不从数据库假设倒推。
- 工具：Excel、Markdown 表格或 DOCX 表格。
- 必填列：实体/页面、字段、字段类型、必填、来源/默认/联动、下游使用、待确认。
- 关系规则：识别来源页面、带出字段、子表、下游页面。

### 流程图/泳道图

- 方法：从业务角色、页面清单、数据对象和交接节点生成，不从文件夹名或固定模板生成。
- 工具：根据用户偏好选择。需要可编辑源文件时可用 next-ai-draw-io / draw.io MCP；需要客户展示美观度时优先用本地绘图脚本、PPT/图片生成或其他可控排版方法；只在轻量文本预览时使用 Mermaid。
- 推荐 MCP 配置：`npx @next-ai-drawio/mcp-server@latest`。
- 检查：流程叙述中必须出现本项目的核心业务对象；不得出现范围外对象。所有连接线必须通过自动检查或人工检查确认无斜线、无明显穿字、无箭头方向混乱。

### Review 与校验

- 方法：先跑结构 harness，再做视觉预览/渲染。
- 工具：`scripts/check_prd.py`、DOCX renderer、macOS QuickLook 降级。
- 输出：通过/失败摘要，包含页面数、表格数、图片数、截图标签数、警告。
- 禁止：只做结构检查时，不要声称已经完成视觉 QA。

## 标准 PRD 结构

除非用户指定客户模板，否则使用以下结构：

1. 引言
   - 1.1 基本信息
   - 1.2 目的
2. 系统概述
   - 2.1 系统描述
   - 2.2 用户定义
   - 2.3 业务流程
   - 2.4 业务框架
   - 2.5 业务角色
   - 2.6 编码/命名/编号规则，适用时加入
   - 2.7 AI能力与数据安全，适用时加入
3. 功能需求
   - 按业务域/角色分组，不写成同级平铺清单。
   - 每个页面包含：标题、类型、字段标记说明、表单布局、明细表、审批/流转、业务规则、待确认、客户截图。
4. 数据与集成要求
5. 待确认事项
6. 附录，可选

页面规则详见 `references/prd-structure.md`。表单整理和结构化规则详见 `references/form-normalization.md`。

## 页面设计规则

- 优先做客户可读的系统表单布局；技术字段清单只作为内部规格的备选。
- `表单样式` 必须接近系统真实页面/报表形态：使用分区标题、字段名/取值规则成对网格、明细子表、跨列长文本等方式表达，而不是简单字段列表。
- 主表建议使用 4 列或 6 列布局，例如 `字段名 | 填写/带出规则 | 字段名 | 填写/带出规则 | 字段名 | 填写/带出规则`；字段名列可加粗或浅灰底，分区标题可合并整行。
- 对既有 PRD 或客户已认可示例进行修订时，优先继承原有表格排版，只调整字号、行高、单元格内边距、标题居中和边框一致性；不要将原有固定网格改造成新的字段分组算法。
- 报表/台账页面应按用户查看的报表列设计，保留表头、筛选/状态字段和一行取值规则示例；不要把报表拆成孤立字段说明。
- 审批意见和签字栏不要放进主表单字段，使用 `审批/流转：...`。
- 客户表单中的长段落如果明显有结构，必须拆成字段或明细表。
- 报表不能误当流程表单，应标为报表页面或数据来源。
- 同一 workbook 多个 sheet 服务不同业务时，必须拆成多个 PRD 页面。
- 例如“门店地图 + 巡检任务 + AI评分”，业务目的不同，应拆成多个页面；如果材料是供应链项目，则按其真实业务拆分。

## 范围自适应与禁写规则

- 写 PRD 前必须先输出“项目范围判断”，包括：项目类型、范围内模块、范围外模块、核心业务对象、主要用户、价值目标、待确认风险。
- 不得因为技能示例、历史项目或 harness 关键词而引入材料中没有的模块。
- 对会议纪要中的背景介绍、商业愿景、竞品案例，应先判断它是功能需求、设计约束、价值目标还是仅供参考；不能把背景案例自动扩展为系统页面。
- 若用户指出 PRD 不相关，必须回到会议纪要重新做范围判断，列出不相关内容和删除理由，再重写。
- 宜搭项目要优先表达宜搭页面形态：表单页、流程页、自定义页面、报表页、地图页、门户页、移动端页面、集成自动化、权限组和消息通知。

## 客户可见表达规则

- PRD、流程图、架构图、封面、摘要和附表都是客户可见产物。不得把用户 prompt、内部工作指令、推理过程、纠错记录、实现过程或“我/你”的对话痕迹写进文档。
- 不要在客户文档里使用生硬的内部免责声明，例如“不是客户生产可用系统”“所有数据都是假数据”“用户要求”“根据你说的”。应转换为体面的项目语言，例如：
  - `能力验证版本`
  - `演示样本数据`
  - `生态协同展示方案`
  - `用于方案演示与价值验证`
  - `后续可按客户真实数据与业务规则迭代`
- Demo/能力展示项目也不要在客户可见正文、图和模块名里反复强调“假数据”“模拟数据”。客户介绍材料应直接使用业务语言，例如 `门店经营数据`、`巡店执行数据`、`交易转化数据`、`健康场景数据`、`经营指标数据`。如确需说明数据环境，应放在交付说明或备注中，用温和表达：`演示环境数据口径后续可按客户真实业务接入调整`，不要放在封面、主流程图或核心卖点页。
- 封面只保留客户愿意转发的内容：客户名称、项目名称、版本、文档类型、日期、编制方/团队（如适用）。背景说明放入引言，不在封面堆过程信息。
- 图中节点必须是业务能力、系统模块、数据对象或价值动作，不出现 `prompt`、`假数据`、`模拟数据`、`演示数据`、`不是落地`、`待我确认` 等内部表达。
- 最终交付前必须搜索客户文档和图源中的敏感过程词：`prompt`、`用户要求`、`根据你`、`我认为`、`不是客户生产可用系统`、`假数据`、`模拟数据`、`演示数据`、`内部`、`纠错`。客户主文档中若出现这些词，必须改为自然业务表达或移除。

## 视觉材料事实锁定

- 用户上传的会议图、纪要截图、白板图、原型图和表格截图是高优先级需求来源。生成 PRD 前必须逐项吸收其中的数字、平台名、链路顺序、状态标签和行动项。
- 不得擅自替换或扩写已明确的平台名、产品名和数字。例如截图写 `200家药店样本`、`千问AI`、`钉钉 -> 高德 -> 闪购/阿里健康 -> 数据回流到钉钉`，就必须按原文进入客户方案；不要替换成 `300家`、`百炼/通义` 或其他旁支能力。
- 如果视觉材料和文字补充发生冲突，优先按用户最新文字修正，并在内部工作记录中更新，不把冲突过程写进客户文档。
- 客户文档中的业务逻辑图应复刻源材料的主链路和层级结构，只有在补充说明中才加入必要的能力解释；不要把非重点能力提升为主模块。

## Harness

运行：

```bash
python scripts/check_prd.py final_prd.docx --min-images 1
```

该 harness 检查必要章节、`3.x.x` 功能页、截图标签、图片数量、字段标记、审批/流转分离和项目逻辑关键词。项目逻辑关键词必须按本项目传入，不得使用固定制造/供应链关键词。它是稳定性门禁，不代表业务内容一定完全正确。

## 完成清单

最终回复前确认：

- 有封面和目录。
- 功能需求按角色/业务域分组。
- 客户提供的 workbook/sheet 已插入截图或明确映射到其他位置。
- 缺失表单有逻辑页面和字段，不是空描述。
- 必填字段、带出/默认/联动字段已标记。
- 截图在对应页面最后。
- 核心业务对象贯穿范围内页面、任务、报表、AI分析和集成。
- PRD 中没有出现范围外模块；若出现，必须能在原始材料中找到依据。
- 流程图/泳道图已按用户偏好生成；若使用 draw.io，应保留 `.drawio`；若使用图片脚本，应保留可复现脚本。图中无斜线、无明显穿字、无范围外对象。
- 待确认问题具体、可让客户回答。
